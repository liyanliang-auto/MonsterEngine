# 2026-08-11 3DGS Vulkan 空白窗口 — 根因定位与修复

## 最终根因（实测，非猜测）
`Include/Renderer/Splat/SplatSortTypes.h` 的 `ERadixScatterBinding` 枚举值与 scatter 着色器
`Shaders/Splat/Sort/splat_radix_scatter.comp` 的 `binding` 编号**完全错位**：

| 枚举名 | 旧值(错) | 着色器 binding | 实际含义 |
|---|---|---|---|
| SortKeysIn    | 0 | 0 | KeysIn ✓ |
| SortValuesIn  | 1 | 2 | ValuesIn ❌ |
| Histogram     | 2 | 4 | HistogramBuf ❌ |
| SortKeysOut   | 3 | 1 | KeysOut ❌ |
| SortValuesOut | 4 | 3 | ValuesOut ❌ |

`SplatSortPass.cpp` 用枚举名 `updateStorageBuffer(ERadixScatterBinding::X, m_xxxBuffer, ...)` 绑定，
所以错误的值把 `m_values*`/`m_keys*`/`m_histogram` 写进了错误的 descriptor 槽：
- 着色器 `ValuesOut`(slot3) 实际收到 `m_keysOdd` → 排序后的高斯索引被写进了 keys 缓冲
- 着色器 `KeysOut`(slot1) 实际收到 `m_valuesEven` → **排序后的 KEYS（低32位=depthBits≈1.07e9）被写进了 values 缓冲**
- 于是 `getSortedValues()` 返回的是 key 的 depthBits 当浮点 ≈1.9，渲染用垃圾索引 OOB 读 → 所有高斯被 EWA
  丢弃 → alpha=0 → 灰背景。DIAG 实测 `garbage=2048/4096`、`first32 raw value≈1072501666`（正是 floatBitsToUint(1.9)）。

## 修复（已应用）
将枚举值对齐到着色器 binding：`SortKeysIn=0, SortKeysOut=1, SortValuesIn=2, SortValuesOut=3, Histogram=4`。
单点修改，无字面量硬编码，15 处引用自动全部修正。

## 根因确认（2026-08-11 下午）：Present Pass 全屏三角形被背面剔除 —— 即灰屏主因

用户提出假设，已逐项核对源码**确认成立**：

### 证据链（全部从源码核实，非仅日志）
1. **引擎默认 frontFace=CW + cullMode=Back**：
   - `RHIDefinitions.h:479` `ECullMode cullMode = ECullMode::Back;`
   - `RHIDefinitions.h:490` `bool frontCounterClockwise = false;`（CW 为正面，注释 L468 明确）
   - `VulkanPipelineState.cpp:917-925` 映射：`cullMode` 默认→`VK_CULL_MODE_BACK_BIT`，`!frontCounterClockwise`→`VK_FRONT_FACE_CLOCKWISE`
2. **present PSO 继承该默认**：`SplatSceneApplication.cpp:563` `PipelineStateDesc desc;` 仅设 vert/frag/topology/depth，未覆盖 `rasterizerState.cullMode` → present PSO = Back+CW
3. **present viewport 实际是 Y-flip（h=-720）**：`SplatSceneApplication.cpp:226-231` 设 `height=+m_windowHeight`，但 `VulkanPendingState.cpp:356-358` 在 `prepareForDraw` 里**无条件** `vkViewport.y = y+height; vkViewport.height = -height;` → 下发 Vulkan 的 height 恒为负（Y-flip）。日志 "vkCmdSetViewport with Y-flip ... h=-720" 印证，且该 Y-flip 对所有 draw（含 present）生效
4. **全屏三角形顶点 CCW（NDC）**：`splat_present.vert:6-10` `(-1,-1)→(3,-1)→(-1,3)`，signed area=+16 → NDC(y-up) 下 CCW

### 绕序数学（显式）
framebuffer 变换（Vulkan y-down）：`x_f=(x_ndc+1)*640; y_f=(y_ndc+1)*(-360)+720`
- v0=(-1,-1)→(0,720)；v1=(3,-1)→(2560,720)；v2=(-1,3)→(0,-720)
- W=(x1-x0)(y2-y0)-(x2-x0)(y1-y0)=2560·(-1440)<0 → **framebuffer(y-down) 下 CCW**
- frontFace=CW → CCW=背面；cullMode=Back → 剔除 → **三角形整片被剔除，0 像素写入**

### 为何解释灰屏
三角形被剔除 → present frag 不写任何像素 → swapchain 仅显示清屏暗灰 `(0.1,0.1,0.15)`。与"无论 splat 数据对错都灰屏"完全吻合，且独立于数据链路（枚举已修、数据已对）。

### 修复（已应用 2026-08-11 08:04）
`SplatSceneApplication.cpp` `initPresentPass()`，`PipelineStateDesc desc;` 之后已加（L564）：
```cpp
desc.rasterizerState.cullMode = ECullMode::None;  // 全屏三角形：禁用背面剔除（Y-flip viewport + CW 正面会把 CCW 三角形判为背面剔除，导致灰屏）
```
全屏三角形禁用剔除是标准做法（也可翻转绕序 CW 以贴合引擎 CW 约定，但 None 最简单稳健）。改完重编 cpp 即可，无需重编着色器。

## 白屏新症（2026-08-11 08:07 运行后）：swapchain 从未 acquire → 图像以 UNDEFINED 布局呈现

灰屏修成白屏（剔除修复生效，三角形现在在画）。新日志（crash.txt 10.5MB，<1 秒几百帧）暴露真正阻断上屏的同步问题：

### 根因（源码核实）
`SplatSceneApplication::onRender()` **漏调 `context->prepareForNewFrame()`**。
- `VulkanDevice::present()` 注释（VulkanDevice.cpp:608）明确："Image acquisition is now done in FVulkanCommandListContext::prepareForNewFrame()"，即 present 假定 acquire 已发生。
- `prepareForNewFrame()`（VulkanCommandListContext.cpp:69-72）内调 `acquireNextSwapchainImage()`：设置 `m_currentImageIndex` + 等待 in-flight fence。
- 正常参考实现 `TriangleApplication::onRender`(L95) / `CubeSceneApplication::onRender`(L499) 都在 `cmdList->begin()` 前调 `context->prepareForNewFrame()`；SplatSceneApplication 漏了。
- 主循环走 `Application::run()→tick()→onRender()`（Application.cpp:134-165），Engine::run() 只跑一帧且 render() 也不 acquire → 无帧同步，紧循环狂跑。

### 日志铁证（crash.txt）
- `VUID-VkPresentInfoKHR-pImageIndices-01430`：present 图像必须在 PRESENT_SRC_KHR，实际是 **UNDEFINED** → 驱动显示为**白**
- `image at index 1 was not acquired from the swapchain` → 从未 `vkAcquireNextImageKHR`
- `vkResetCommandBuffer/BeginCommandBuffer ... is in use`、`VkFence already in use`、`semaphore has no way to be signaled` → 没有等 in-flight fence，命令缓冲/信号量在 GPU 占用时被复用

### 灰→白机制
之前三角形被剔除，render pass 仍 clear 交换链；现在真在画，但同步全错 → 提交的图像以 UNDEFINED 布局被 present → 白。本质是"present 链路同步坏"，只是现在真正画东西，错乱表现为白。

### 次要问题
1. `diagnoseRenderState()` 帧中 `cmdList->end(); submitAndWait(); cmdList->begin()` 中途打断命令缓冲，干扰单帧 begin/end/submit，是 "command buffer in use" 的助推因素。应临时 early-return 关掉。
2. init 时 present PSO 创建报 `VUID-VkGraphicsPipelineCreateInfo-stage-02096: no stage contains a Vertex Shader` → 若 `m_present.pipelineState` 为 null，present draw 成 no-op；修好同步后若仍灰（清屏色）而非点云，则需核对 `desc.vertexShader` 是否正确接进图形管线。

### 修改方案（待用户确认，尚未改）
1. 【主因】`SplatSceneApplication::onRender` 顶部（拿到 `context` 后、`cmdList->begin()` 前）加 `context->prepareForNewFrame();`
2. 【干扰】`diagnoseRenderState` 直接 early-return 空函数
3. 【验证】确认 present PSO vertex shader 正确接入；若 PSO 为 null 先修管线接线
仅改 cpp，无需重编着色器。

## 用户对"白屏"的二次分析评估（2026-08-11，本机复核源码）

用户提出：present PSO 缺 Vertex Shader（`Created 1 shader stages: Stage[0]: type=16` 仅 fragment）→ TSharedPtr 多重继承指针调整导致 `getShaderModule()` 返回 VK_NULL_HANDLE → 残缺管线 → draw 失败 → swapchain 错乱 → 白屏。

### ✅ 用户对的部分（症状真实）
- present PSO 确实只有 1 个 stage、缺 VS（`MonsterEngine.log:228-229` 实测 `Created 1 shader stages / Stage[0]: type=16`）。这是**独立真实 bug**，与剔除修复无关。
- VUID-06896/02096（crash.txt L8-11）确实报"无 vertex shader"。

### ❌ 用户错的部分（机制与因果）
1. **TSharedPtr 多重继承指针调整假说不成立**：
   - `VulkanVertexShader : public VulkanShader, public IRHIVertexShader`（VulkanShader.h:70），`VulkanShader` 是**第一基类（offset 0）**。
   - `getShaderModule()` 是 **非虚** 成员（VulkanShader.h:41），定义在第一个基类 → `this` 调整为零，访问 `m_shaderModule` 正确。
   - `static_cast<VulkanVertexShader*>(irhiVSptr)` 由编译器按已知 MI offset 调整，必正确，不会产出野指针；TSharedPtr 拷贝保留同一 `IRHIVertexShader*`，调整只在 cast 时发生且正确。
2. **因果链倒果为因**：同步错乱（image not acquired / cmd buf in use / fence in use）来自 `onRender` 漏调 `prepareForNewFrame()`（已核实的独立 bug），与 VS 缺失无关。缺 VS 的 draw 不会产生 acquire/fence 错误。
3. **"灰→白因 cull 改动弄丢 VS" 自相矛盾**：灰→白两轮之间唯一改动是 `cullMode=None`，`desc.vertexShader = m_present.vertexShader` 赋值未变 → present PSO 两轮 stage 数相同。若本轮 1 stage（无 VS），上轮也是 1 stage → 两轮 present 都不画 → 都应是清屏灰。白=UNDEFINED 布局 present=同步 bug，与 VS 无关。用户称"上轮 2 stage"在不变代码下不可能，疑为别处日志/误记。

### ⚠️ 真正"VS 为何丢失"仍未定位（静态无法解）
- 赋值正确（SplatSceneApplication.cpp:565）、创建成功（无 Failed 日志、pipeline 建起）、`PipelineStateDesc` 用默认拷贝构造（RHIDefinitions.h:685，正确拷贝 TSharedPtr）、cast/getShaderModule 正确 → 静态看应产 2 stage。
- `createShaderModules`（VulkanPipelineState.cpp:157-173）对"VS 缺失"**无 else 报错分支** → 静默跳过，正是难查原因。
- 真因需运行时日志：在 `if(m_desc.vertexShader)` 加 else 报 "no VS assigned"，在 `if(vertexModule!=VK_NULL_HANDLE)` 加 else 报 "VS module null"。用户提案"修改1"（加诊断日志）此处有用；"修改2"（keeper shared_ptr）是 no-op（m_present 已保活）；"修改3"（ctor 日志）与修改1 冗余。

### 结论与优先级
- **白屏主因 = 漏调 prepareForNewFrame（同步）**，先修（一行）。
- **present PSO 缺 VS = 第二个独立真实 bug**，也要修（否则同步修好后仍因无顶点而灰清屏）。但用户给的修复方案（基于错误机制）无效。应先用诊断日志定位 VS 真正丢失点，再针对性修。

## 关掉 GPU-AV 后窗口仍"未响应/挂起"（2026-08-11 20:33 再次运行）

用户：关掉 validation 后点云仍渲染出来了，但鼠标移到窗口光标转圈、窗口栏"未响应"、任务管理器显示进程已挂起。

### 结论（重新读日志+源码，实证）
**程序没有死锁，是健康循环（约 70fps），但"挂起"是渲染主线程被持续饱和 + 缺乏帧节流（frame pacing）导致 Windows 标记未响应，并存在 TDR 挂起风险。**

铁证：
1. 新 crash.txt **L1 已无 GPU-AV 警告** → validation 已关（上次修改生效）。
2. crash.txt 仅 85 行，帧在持续循环（ViewMatrix→Pass1-6→draw→下一帧），**Grep 全文件无任何 VUID/Error/fence/timeout/同步错误** → 同步/验证层均正常。
3. 日志被截断在某一帧绘制中（`VulkanCommandList...` 半行）→ 是被用户杀进程中断，非死锁停在某帧。
4. 日志时间戳逐帧 CPU 耗时：帧1(含排序初始化+首帧 GPU 回读)=419ms；帧2/3/4 ≈ 3–4ms；帧间隔 12–19ms ≈ **~70fps**。说明**稳态下 GPU 帧 ≈ 12–15ms，远未到 TDR 2s 上限**，但 CPU 每帧都在满负荷提交。
5. 同步架构核实：`acquireNextSwapchainImage()` 确有 `vkWaitForFences(...,UINT64_MAX)`（VulkanCommandListContext.cpp:140/170）→ CPU 会等 GPU 完成才推进；呈现模式优先 `MAILBOX`（VulkanDevice.cpp:1273-1274）→ present 不阻塞 CPU；`present()` 注释明确"不调 vkQueueWaitIdle"（L662-663）。
6. `Application::run()`(Application.cpp:134) 是纯 `while{ tick(); }` **忙等循环，无 sleep / 无帧节流 / 无 vsync 让出**；`tick()`(L142) 每帧调 `glfwPollEvents()`（非阻塞）。

### 机制（为何健康循环仍"未响应/挂起"）
- 忙等循环把单 CPU 核跑满（持续 70fps 提交），即便每帧 pollEvents，Windows 在 hover 时做命中测试/光标响应拿不到及时回应 → 光标转圈 + 标题"(未响应)"。
- `MAILBOX` 不阻塞 CPU + 无 sleep → CPU 疯狂提交，GPU 队列积压；一旦某帧（尤其相机移动后更多高斯/排序重排）GPU 时间超出 TDR 2s → 驱动重置 → 进程线程被挂起（"进程已挂起"）。
- 1.15M 高斯对调试迭代过大，单帧 GPU 波动可能触发偶发长帧。

### 修改方案（用户要求"先不修改"，已分析给方案）
1. **【主因·必须】给主循环加帧节流 / 让出 OS**：`Application::tick()` 末尾或 `run()` 循环里，按目标帧率（如 60fps）`std::this_thread::sleep_for` 补足帧间隔，或改用 `glfwWaitEventsTimeout`。→ 线程让出、消息泵饱和解除、"未响应"消失；同时抑制 CPU 100% 与 GPU 队列积压。
2. **【稳妥·可选】强制 FIFO 呈现模式**：VulkanDevice.cpp:1273 把 `VK_PRESENT_MODE_MAILBOX_KHR` 偏好去掉，始终用 `VK_PRESENT_MODE_FIFO_KHR`（L1271 默认）。FIFO 让 present 阻塞到 vblank，天然把 CPU 限制在 ~60fps 并随 vblank 让出线程。前提是稳态 GPU 帧 <16ms（实测 ~12–15ms，成立）。
3. **【调试效率·建议】缩小调试数据集**：1.15M 高斯对本地迭代过重，换小场景（如 indoor baseline 数万高斯）使单帧 GPU 远小于 TDR，交互顺滑并降低长帧挂起概率。
4. **【清理·建议】移除调试残留**：`diagnoseRenderState` 早退；`splat_render.comp` 诊断色还原 `vec4(C,1.0-T)` 并重编。

仅方案1、2 动 cpp（无需重编着色器），方案3 换数据，方案4 重编着色器。

注：日志只覆盖约 470ms 健康运行，"挂起"本体未落在日志内；以上为基于架构+时间戳的实证推断，最高确定性结论是"无死锁、同步正常、需加帧节流"。
